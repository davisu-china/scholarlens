ScholarLens 面试准备手册

怎么把这个项目讲清楚、讲出深度、扛住追问。每个问题都给出标准且靠谱的回答——全部与真实实现（六边形架构、混合检索、NLI 引用校验、覆盖度驱动的研究 Agent、B0→+6 消融）一致，不夸大、不编造数据。

01项目自述（电梯稿）

准备三个长度的版本，按面试官给的时间选用。核心是先说清解决什么问题，再说关键技术决策，最后给可量化结果。

30 秒版（一句话 + 三个支点）

ScholarLens 是一个面向学术文献的可溯源深度研究引擎：解析论文 PDF、沿引用关系做多跳检索，生成带引用的研究综述，每一句结论都能追溯到原文的页码和坐标框。它解决通用 RAG 处理学术文献的三个硬伤——解析失真、单跳检索不够、引用不可信。关键做法是：版面感知解析 + 多粒度混合检索 + 生成后用 NLI 逐句校验引用是否成立。

2 分钟版（问题 → 方案 → 亮点 → 结果）

  1. 问题：研究者做文献调研，通用 RAG 有三个痛点——PyPDF 提取双栏/公式会串栏乱码；一次 Top-K 覆盖不了"方法 A 与其改进 B 的差异"这类多跳问题；LLM 常编造论文标题或张冠李戴，核对起来反而更慢。
  2. 方案：离线用 MinerU 做版面解析保留公式/表格/坐标，归一成统一的 Document IR；建四层多粒度索引并对每个 chunk 加上下文前缀；在线走四路混合召回（Dense+Sparse+表格+引用图）+ RRF 融合 + Cross-Encoder 重排。
  3. 亮点：两个差异点——① 深度研究 Agent 用"证据覆盖度"而不是固定轮数决定何时停止补检索；② 引用校验，生成后对每条引用做 NLI 蕴含判定，不达标的句子让模型依据证据重写，可信度可量化、引用精确到 bbox。
  4. 结果/工程：整套用六边形架构，外部系统全部抽象成接口、各有真实实现和内存假实现，核心逻辑有 55 个单测、可一键评测；设计目标是证据召回比朴素向量检索提升 25%+、引用准确率 ≥0.9（以消融实测为准）。
讲法要点：自述里主动埋 2-3 个"钩子"（NLI 校验、覆盖度停止、六边形架构），引导面试官往你最熟的点追问，掌握主动权。

02项目解读与叙事线

被要求"介绍一下你的项目"时，不要按模块罗列，要按一条叙事线讲，让面试官跟得上。

推荐叙事线：一个查询的生命周期

用"用户问一个问题，系统怎么一步步给出可信答案"串起所有模块，自然覆盖解析、索引、检索、生成、校验：

阶段讲什么能带出的技术点
离线建库PDF → 版面解析 → Document IR → 多粒度切分 + 上下文前缀 → 写三个库MinerU、IR 解耦、Contextual Chunking、Qdrant/Neo4j/Postgres 分工
Query 理解路由到 factoid/numeric/survey/paper_specific 四类，走不同检索组合意图分类、survey 自动进深度研究
混合检索四路并发召回 → RRF 融合 → Cross-Encoder 重排 → 父块扩展RRF 为何优于加权、Small-to-Big
受约束生成每句以 [eid] 结尾，eid 只能取自给定证据反幻觉的第一道闸
引用校验切句 → NLI 蕴含判定 → 数值规则校验 → 不达标重写 → 定位 bbox项目最核心差异点

画架构图的顺序

白板讲架构时，按"离线/在线分离"切两块画，别一股脑铺：

  • 先画一条横线分离线 Ingestion（Celery 异步，重、慢、可重试）和在线 Query（低延迟、流式）——先讲清为什么要分，体现你懂负载特性。
  • 再画存储层四个库，每个一句话职责（向量/图/关系/对象）。
  • 最后点一句六边形架构：这些外部系统我都抽象成了接口，换 Qdrant 还是别的只改一个 adapter——这是体现工程成熟度的句子。
一个让面试官印象深刻的细节：主动说"我没有把界面做成全 Python 的 Reflex，而是独立的 Next.js，因为三栏联动 + PDF bbox 高亮这类交互 Reflex 生态吃力"——展示你对选型做过真实权衡，而不是跟风。

03项目亮点

把项目拆成 5 个可以独立深挖的技术点。每个点都按是什么 → 为什么这么做 → 怎么实现 → 数据/效果准备，面试官追到哪一层都能接住。

① 版面感知解析 + 统一 Document IR

是什么：用 MinerU 把 PDF 切成带类型的 block（标题/正文/公式/表格/图注），公式转 LaTeX、表格转 HTML，每个元素保留页码和坐标框；所有解析器输出归一到同一个 Pydantic 模型 PaperIR。

为什么："解析质量决定 RAG 效果的上限"——提取阶段串栏、公式乱码，后面检索再强也没用。统一 IR 让下游只依赖 IR，换解析器不用改下游代码。

怎么实现：行内公式以 LaTeX 内联进文本，独立公式额外生成一句自然语言描述一起入索引，这样用户用自然语言也能检索到公式。

效果：消融表 B0（PyPDF+固定切分）→ +1（MinerU+按章节切分）这一行量化它的收益。

② Contextual Chunking（上下文前缀）

是什么：入库前为每个 chunk 生成 50–100 token 的上下文前缀，把前缀和正文一起做 embedding 和 BM25。

为什么：解决 chunk 缺主语无法被召回——"该方法提升 2.3 个点"这种句子单独看检索不到，补上"本段出自 YaRN §5.2 长文本实验"就能召回。

工程细节：前缀生成用 prompt caching，同一篇论文全文只缓存一次，每个 chunk 的调用成本降约 90%——这是能体现"考虑真实成本"的细节。

③ 深度研究 Agent：按覆盖度停止

是什么：Plan→Research→Reflect→Write→Verify 的带循环状态机。关键是 Agent 知道何时停：Reflector 为每个子问题列出"需要哪些信息点"，覆盖度 = 已覆盖/总信息点，不足则把未覆盖项转成下一轮的补充查询（≤3 轮）。

为什么好：比"固定搜 N 轮"更省、更准——补检索有明确目标，不会让模型泛泛地"再搜一搜"。

成本控制：Planner/Writer 用强模型，Reflector/改写用小模型；子问题并行；会话内检索结果按 query embedding 余弦 >0.95 缓存，目标单次深度研究 <$0.15。

④ 句级引用校验（最核心差异点）

是什么：普通 RAG 只"让模型带引用"；ScholarLens 在生成之后验证每条引用是否成立。五步：受约束生成（句尾 [eid] 且合法）→ 切成论断-引用对 → DeBERTa-NLI 判定 P(证据蕴含论断) → 数值类再做"数字必须在原文出现"的规则校验 → 蕴含概率低于阈值的句子让 LLM 依据证据重写一次，仍不过则标红。

为什么是护城河：学术场景里"引用不可信"是致命伤。这套把"幻觉"从不可控变成可度量——每个答案给可信度评分（如"92% 的论断有直接证据"），引用精确到 bbox。

阈值怎么定：NLI 阈值 0.5 是初始值，上线前在 200 条人工标注的"论断-证据"对上按 Precision 优先重新标定。

⑤ 六边形架构 + 评测驱动

是什么：所有外部系统（向量库/图库/LLM/Embedder/Reranker/NLI/解析器）抽象成 Protocol 接口，每个接口有真实 adapter 和内存 fake。

为什么：① 可测——用 fakes 不依赖 GPU/Docker 就能端到端跑 55 个单测；② 可扩展——换后端只改一个 adapter；③ 可读——业务逻辑和 IO 彻底分离。这是把"学生项目"和"工程项目"区分开的东西。

04技术挑战

面试官爱问"你遇到最大的挑战是什么"。准备 3-4 个真实、有技术含量、你主导解决的，每个按"难在哪 → 几种方案 → 为什么选这个 → 代价"讲。

挑战一：四路召回的分数不可比

Dense、Sparse、表格、引用图四路召回，分数尺度完全不同，怎么融合？
加权求和要调权重、对分布敏感、换数据就失效。我用 Reciprocal Rank Fusion：score = Σ 1/(k+rank)，只看每路里的排名不看分数，对尺度天然不敏感、k=60 基本无需调参。代价是丢失了分数的绝对强度信息，所以 RRF 之后再接一层 Cross-Encoder 重排把精度找回来。

挑战二：chunk 缺主语召回不到

"该方法提升 2.3 个点"这种句子检索不到，怎么办？
这是 chunk 独立切分的通病。我用 Contextual Chunking 给每个 chunk 补上下文前缀再索引。难点是成本——每个 chunk 都调一次 LLM 太贵，用 prompt caching 把同一篇论文全文缓存一次，单 chunk 成本降约 90%。

挑战三：怎么保证"引用"真的成立

模型会编造引用，你怎么从机制上杜绝？
分两道闸：生成时用受约束 prompt 让 eid 只能取自给定证据、再用正则校验合法性（挡住编造 id）；生成后用 NLI 判定证据是否真的蕴含该句（挡住"id 合法但内容对不上"）。数值类再加硬规则——数字必须在原文出现。三者叠加，把引用正确性做成可度量的指标而不是祈祷。

挑战四：Agent 不收敛 / 成本失控

研究 Agent 容易无限循环或烧钱，你怎么控制？
用覆盖度而非固定轮数作为停止条件，并硬性封顶 3 轮；大小模型分工（规划/写作用强模型，反思/改写用小模型）；子问题并行；会话内语义缓存。状态用 checkpoint 持久化，支持人工编辑研究计划后恢复（human-in-the-loop）。

07问答预判 · RAG 与检索

RAG 的 chunk 大小怎么定？
没有万能值，取决于内容密度和问题粒度。我用多粒度回避这个两难：L0 整篇、L1 章节、L2 ~400token 段落、L3 表格/公式元素，父子关联。精确召回用小块，送 LLM 时用 Small-to-Big 扩展到所在段落，兼顾召回精度和上下文完整。
为什么要 Sparse 检索，Dense 不够吗？
Dense 擅长语义相似，但对专有名词弱——"YaRN""LongBench""NQ"这类模型名/数据集名，Dense 容易漏，Sparse（BM25/SPLADE）靠精确词匹配能召回。学术场景专有名词极多，所以必须双路。举例：问"YaRN 的困惑度"，Dense 可能召回一堆讲困惑度的无关段落，Sparse 能把含"YaRN"的段落顶上来。
RRF 的 k=60 是怎么来的？
RRF 原论文的经验值，作用是平滑高排名项的影响、降低对单路头部结果的过度依赖。它不敏感、改动收益很小，所以我没花精力调它，把调参预算放在更有收益的重排微调上——这也体现一种工程判断：不是所有超参都值得调。
重排器为什么要微调？怎么构造训练数据？
通用 reranker 对学术领域的"证据 vs 相关但非证据"区分不够细。我用 QASPER 训练集的(问题,证据段)作正样本，BM25 检索出的高分非证据段作难负样本，对 bge-reranker 做 LoRA 微调。难负样本是关键——用随机负样本学不到细粒度区分。
检索召回不到正确证据（漏召回）怎么排查？
进 bad case 池后按链路定位：先看 Dense/Sparse 各自的 top100 里有没有 gold 证据——如果都没有是召回问题（可能 chunk 缺上下文、或 query 需要改写/HyDE）；如果召回有但 RRF/重排后掉出 top10，是排序问题。四类归因（解析/召回/排序/生成）就是干这个的。

08问答预判 · Agent 与引用校验

覆盖度具体怎么算？会不会 LLM 自己说"覆盖了"就过？
Reflector 先为子问题列出需要的信息点（如"PI 的困惑度""PI 的训练成本"），再逐项判断现有证据是否覆盖，覆盖度=已覆盖/总数。判定我设计成可注入的谓词——可以用 NLI 或 embedding 相似度，不是让 LLM 拍脑袋说"够了"。未覆盖的信息点直接变成下一轮的检索 query，保证补检索有靶子。
NLI 校验会不会太慢？延迟能接受吗？
DeBERTa-NLI 单对约 15ms，GPU 批量推理。一个答案通常 10-20 句，批处理一次就算完，加在生成之后对总延迟影响小。而且它只在深度研究/高价值答案上必跑，快速问答可配置开关。
NLI 判成"不蕴含"但其实是对的（误杀）怎么办？
这是 precision/recall 的权衡。我的策略：阈值按 Precision 优先 标定（宁可漏标一些真引用，也别放过假引用，因为学术场景假引用代价更高）；不达标的句子先自动重写一次而不是直接删，给它一次改正机会；仍不过才标红让用户知道。阈值在人工标注集上定，不是我拍的。
为什么不直接让 GPT-4 带引用就行，非要加 NLI？
因为"让模型带引用"和"引用成立"是两回事——模型完全可能给一个格式正确、但内容对不上的 [eid]。受约束生成只能保证 id 合法，保证不了语义蕴含。NLI 是独立的第二道验证，把"相信模型"换成"验证模型"。这正是这个项目和普通 RAG demo 的分水岭。
LangGraph 相比自己写循环，到底多了什么？
三样我实际用到的：①interrupt() 让计划阶段能停下来等用户编辑再继续；②checkpoint 持久化，长研究中断了能恢复；③状态在并行子问题分支间的合并（reducer）。自己写循环这些都要手搓且容易出错。诚实补充：我的核心控制逻辑写成了独立的协调器，不强依赖 LangGraph，这样逻辑能单测——LangGraph 是对它的一层绑定。

09问答预判 · 工程与系统设计

为什么用了四个数据库，不嫌重吗？
每个职责不可替代：Qdrant 存向量做混合检索；Postgres 存元数据、表格四元组（数值问答要跑 SQL）、Agent 的 checkpoint；Neo4j 存引用图（引用是天然的图，多跳扩展比关系库递归 JOIN 自然）；MinIO 存 PDF 原件。但我也承认 MVP 可以砍——Qdrant+Postgres+Redis 就能起步，Neo4j（引用图谱是 P1）和 MinIO 可以延后。知道什么时候上什么，比一上来全铺更重要。
离线解析和在线查询为什么要分开？
负载特性相反。解析一篇要跑版面检测/公式识别/embedding，重、慢（目标<20s）、可失败重试——必须异步化（Celery+Redis），不能卡在 HTTP 请求里。查询要低延迟流式（首 token P95<1.5s）——走同步 API+SSE。混在一起会互相拖累。
六边形架构具体怎么落地的？好处是什么？
所有外部系统定义成 Protocol（Embedder/VectorStore/LLM/NLI…），业务逻辑只依赖接口。每个接口两个实现：真实 adapter（Qdrant 等）和内存 fake。好处立竿见影——① 55 个单测用 fakes 跑，不要 GPU/Docker 就能验证检索/校验/Agent 全链路；② 换向量库只改一个 adapter；③ 一个 composition root 统一装配，环境变量切真假。
这个系统怎么扩展到百万级论文？瓶颈在哪？
瓶颈主要两处：①离线解析吞吐——Celery 横向加 worker、GPU 池化；②向量检索延迟——Qdrant 的 payload 过滤下推 + HNSW 参数调优，必要时按 collection 分片。在线侧用语义缓存挡重复查询。元数据过滤在召回阶段就下推到 Qdrant，避免召回一大堆再过滤。
怎么保证评测可复现？
评测数据集、Prompt、模型版本统一版本管理，每次评测结果写进 eval_runs 表（带配置快照）。同一个 make eval 命令任何人任何时候跑结果一致。CI 把它接成门禁。

10问答预判 · 拷打与诚实题

这些是"压力测试"，考你的技术诚实度和边界感。答这类题的原则：先给真实边界，再给应对，绝不吹。

你这些指标（Recall 0.85、引用准确率 0.9）实测跑出来了吗？
如实说：这些是设计目标值，评测框架和消融脚本已经搭好（eval/），数值要在真实模型和数据上跑消融后填入——目前核心逻辑用 fakes 做了端到端验证（55 单测），真实模型联调还在进行。我不会给你一个没跑出来的数字。
哪部分是你真写了，哪部分还是设计？
直接给清单：检索/索引/引用校验/研究 Agent/评测的业务逻辑都实现并测过；真实 adapter（Qdrant/Neo4j/BGE/DeBERTa/MinerU）照接口写好、结构契约测过，但与真实服务和模型的联调需要 GPU/Docker 环境；MinerU 的版面产物映射留了明确的 TODO，因为不同版本字段不一样。（见下一章"诚实边界清单"）
如果 MinerU 解析质量不行，你整个系统不就垮了？
对，解析是上限，这也是我把它排在最高优先级、并用 B0→+1 消融专门量化它的原因。缓解手段：统一 IR 让解析器可替换（MinerU 不行可换 Nougat 等）；解析失败的文件进重试队列；关键是早点用消融数据暴露解析环节的收益/损失，而不是假设它完美。
这个项目和市面上的 RAG 框架（LangChain 那种）比，你的价值在哪？
框架给的是通用组件；我的价值在针对学术场景的端到端设计决策：版面感知解析、多粒度+上下文切分、四路混合、以及最核心的生成后 NLI 引用校验。拿 LangChain 也能搭个 demo，但"引用可溯源到 bbox 且经过验证"这套反幻觉机制是我自己设计的，不是调个库就有的。
你一个人做的？哪些是你独立完成的？
（按真实情况答）如实说明你负责的部分和借助的工具/参考。诚实比"全是我写的"更可信——面试官一追代码细节就露馅。重点讲你做决策的地方：为什么这么切分、为什么加 NLI、为什么选 Qdrant，这些是抄不来的。
诚实题通用模板："这部分我做到了 X（具体、可验证）；Y 还没做/是设计（明确边界）；如果要做 Y，我会这样做（给方案）。" —— 三段式既不虚、又展示你想清楚了。

11诚实边界清单

把"实现到什么程度"心里有本账，被问到任何部分都能准确回答，不含糊、不夸大。

模块状态被追问时怎么说
混合检索 / RRF / 路由已实现+测RRF、四路编排、父块扩展都有，用 fakes 端到端测过；四路的真实后端是 Qdrant adapter
多粒度切分 / 上下文前缀已实现+测L0-L3 切分实现并测；上下文前缀逻辑在，真实前缀需接 LLM
引用校验（NLI）已实现+测切句/蕴含判定/数值校验/重写/可信度全有；真实判定接 DeBERTa
研究 Agent 协调器已实现+测Plan→Research→Reflect→Write→Verify 完整，覆盖度停止逻辑测过
评测（指标/消融/runner）已实现+测指标纯函数测过，消融矩阵 B0-6 定义好，runner 能跑
真实 adapter（Qdrant等）写好/契约测照接口实现、结构契约测过；与真实服务/模型的功能联调需本地环境
MinerU 解析映射留 TODOIR 映射骨架在，_run_mineru 需按所用 MinerU 版本补字段——诚实说明原因
指标数值设计目标是目标值不是实测，务必强调"以消融实测为准"

12面试前自检

能不看稿讲出来

  • 30 秒 / 2 分钟自述各一遍
  • 白板画架构（离线/在线分离 → 存储 → 六边形）
  • 一个查询从进来到带校验答案的全链路
  • 引用校验五步，能讲到代码级

每个选型能说清备选局限

  • Qdrant vs pgvector（百万级+过滤）
  • RRF vs 加权融合
  • BGE-M3 一次出 dense+sparse 的价值
  • Next.js vs Reflex 的真实权衡

数据与诚实

  • 指标是"目标值"，脱口而出不漏这句
  • 实现 vs 设计的边界清单记牢
  • 被拷打用三段式：做到X / Y没做 / 会怎么做

反问面试官（加分）

  • 你们线上 RAG 怎么评估幻觉？
  • 检索和生成的延迟预算怎么分？
  • 长文档/多跳问题你们怎么处理？
最后一句心态提醒：这个项目真正的深度在"为什么这么做"和"我验证了没有"，不在"用了多少技术名词"。把决策讲透、把边界讲诚实，比背参数更能打动懂行的面试官。
