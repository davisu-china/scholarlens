Part I · 产品需求 PRD

01项目概述

通用 RAG 处理学术文献时会出现三类问题。ScholarLens 针对这三类问题设计。

∑

解析失真

论文里双栏排版、LaTeX 公式、跨页表格和图注很常见。用 PyPDF 提取会出现串栏、公式乱码、表格结构丢失，后续检索得不到正确内容。

⟲

单跳检索不够

"方法 A 和后续改进方法 B 在长文本上表现有何差异"这类问题，需要跨多篇论文、沿引用关系逐步取证。一次 Top-K 检索覆盖不了。

✓

引用不可信

LLM 常编造论文标题，或者把 A 论文的结论标到 B 论文上。研究人员必须逐条核对，节省的时间所剩无几。

产品定位

一句话：帮研究人员在一个可信的私有论文库上，用 10 分钟完成过去需要 2 天的文献调研。

项目目标

维度目标衡量方式
检索质量证据段召回率比朴素向量检索提升 25% 以上QASPER evidence Recall@10，消融实验
答案可信引用准确率 ≥ 0.90，无据结论占比 < 5%NLI 自动校验 + 200 条人工抽检
研究效率生成一篇 3000 字综述 < 3 分钟端到端计时，LangSmith / Langfuse trace
工程质量可一键部署、可观测、可复现评测docker compose up，评测脚本接入 CI

不做什么（Non-Goals）

  • 不训练基座模型；只在 Embedding 和 Reranker 上做可选的领域微调。
  • 不做论文写作或润色，系统只负责"找到证据并组织证据"。
  • v1 不支持多租户计费，鉴权只做单组织的 RBAC。

02目标用户与场景

主要用户是需要大量阅读文献的研究人员，按使用深度分为三类。

◆ 研究生

痛点：刚进入新方向，不知道该读哪些论文，读完也很难串成脉络。

核心场景："给我梳理 RAG 中 Reranker 技术从 2020 年到现在的演进。"

◆ 课题组 / 实验室

痛点：组内共享论文库零散，新人反复问同样的问题。

核心场景：共享知识库，按项目分 collection，查询"组里哪些论文用过 LoRA 在医学数据上做微调"。

◆ 企业研究院

痛点：技术选型要做竞品方法对比，结论必须有出处。

核心场景："对比 5 种长上下文方法在 LongBench 上的结果"，系统输出对比表格并为每个数字标注来源。

用户故事

编号作为…我希望…以便…

03功能需求

功能按优先级分为三档：P0 是 MVP 必须完成的，P1 是体现技术深度的核心亮点，P2 是加分项。

F1 · 文献导入与解析 P0

  • 支持 PDF 批量上传、arXiv ID / DOI 导入，并按 SHA-256 去重
  • 版面分析：识别标题、章节、段落、公式、表格、图注和参考文献
  • 公式转为 LaTeX，表格转为 Markdown / HTML，保留每个元素的页码和坐标框
  • 解析进度通过 SSE 实时推送，失败的文件可以重试

F2 · 快速问答 P0

  • 单轮或多轮问答，流式输出
  • 答案中每个论断后都带 [n] 角标，悬停显示原文片段
  • 可按 collection、年份、作者、会议过滤
  • 证据不足时明确拒答，不编造

F3 · 深度研究模式 P1 · 亮点

  • Agent 先生成研究计划（子问题树），用户可以编辑后再执行
  • 多轮迭代：检索、阅读、反思、补检索，直到证据充分
  • 输出带章节结构的综述，并附对比表格
  • 研究过程可视化：每一步的工具调用、耗时和召回结果

F4 · 句级引用校验 P1 · 亮点

  • 生成后用 NLI 模型逐句校验"引用片段是否蕴含该句"
  • 未通过校验的句子先自动重写，仍不通过则标红提示
  • 每个答案给出可信度评分，比如"92% 的论断有直接证据"

F5 · 表格与数值问答 P1

  • 实验结果表格结构化存储（方法 × 数据集 × 指标）
  • 数值比较类问题先路由到表格检索，再在沙箱中执行 pandas 计算
  • 跨论文汇总生成对比表，每个单元格都标注来源

F6 · 引用图谱 P1

  • 解析参考文献，与库内论文对齐，构建引用图
  • 基于图的扩展检索：从种子论文出发，沿引用 / 被引关系扩展
  • 前端提供交互式图谱，节点大小表示库内被引次数

F7 · PDF 原文对照阅读 P0

  • 内置 PDF 阅读器，点击引用后跳到对应页并高亮坐标框
  • 支持划词提问："解释这个公式"

F8 · 导出与评测面板 P2

  • 导出 Markdown / LaTeX / BibTeX
  • 管理员可在评测面板查看各版本的检索和生成指标趋势
  • 用户的👍/👎反馈进入 bad case 池

07文档解析流水线

解析质量决定了 RAG 效果的上限。这一章的设计目标是：任何一段文本都能还原到原 PDF 的页码和坐标，公式和表格的语义不在解析中丢失。

STEP 1版面检测MinerU（基于 LayoutLMv3 / DocLayout-YOLO）把每页切成 block，类型包括 title、text、equation、table、figure、caption、reference
STEP 2阅读顺序处理双栏和跨栏图表，按 XY-Cut 排序，生成线性文本流
STEP 3元素识别公式用 UniMERNet 识别为 LaTeX；表格用 StructEqTable 识别为 HTML；图像由 VLM 生成描述
STEP 4章节树重建根据标题层级、编号规则（3.1 / 3.1.2）和字号，重建 Section 树
STEP 5参考文献GROBID 输出 TEI XML，再通过 Semantic Scholar API 对齐到 paperId

统一中间表示（Document IR）

所有解析器的输出都归一到同一个 Pydantic 模型。下游模块只依赖这个 IR，因此更换解析器不需要改动下游代码。

ingest/schema.pyclass BBox(BaseModel):
    page: int
    x0: float; y0: float; x1: float; y1: float   # PDF 坐标系，前端用于高亮

class Block(BaseModel):
    id: str
    type: Literal["text", "equation", "table", "figure", "caption"]
    content: str                  # 文本 / LaTeX / HTML 表格 / VLM 图像描述
    bboxes: list[BBox]            # 跨页元素有多个 bbox
    section_path: list[str]       # ["3 Method", "3.2 Frequency-aware Interpolation"]
    refs: list[str] = []         # 块内引用的参考文献 key，如 ["chen2023pi"]

class PaperIR(BaseModel):
    paper_id: str; title: str; authors: list[str]; year: int; venue: str | None
    abstract: str
    blocks: list[Block]
    references: list[Reference]   # 已对齐 S2 paperId 的参考文献
难点与对策：公式经常被行内文本打断，比如 "where $\theta_i$ denotes…"。解析时把行内公式以 LaTeX 形式内联到文本中，同时为独立公式生成一句自然语言描述（"该公式定义了频率相关的插值因子"），并把描述一起写入索引。这样用户用自然语言提问时也能检索到公式。

08多粒度索引

学术问题的粒度差别很大。"这篇论文讲了什么"需要论文级的信息，"公式 3 里的 β 是什么"需要句子级的信息。因此系统建立四层索引，并用父子关系把它们关联起来。

层级单元内容来源典型问题检索用途
L0 Paper整篇论文标题 + 摘要 + LLM 生成的结构化摘要（问题 / 方法 / 结论）"有哪些用对比学习做 Reranker 的工作"粗筛候选论文
L1 Section章节按章节生成的摘要（RAPTOR 风格自底向上聚合）"YaRN 的实验设置是什么"定位相关章节
L2 Chunk约 400 token 段落按语义边界切分，不跨章节，加上上下文前缀大多数事实型问题主要召回单元
L3 Element表格 / 公式 / 图表格行的结构化记录、公式 LaTeX 及其描述、图注"哪个方法在 NQ 上 EM 最高"数值和公式问答

Contextual Chunking

参考 Anthropic 提出的 Contextual Retrieval 方法，入库前为每个 chunk 生成一段 50～100 token 的上下文前缀，把前缀和 chunk 一起做 embedding 和 BM25 索引。例如 chunk 原文是"该方法在 128K 上提升 2.3 个点"，补充前缀后变成"本段出自 YaRN 论文 §5.2 长文本困惑度实验，比较对象为 PI 与 NTK……"。这样能解决 chunk 缺少主语、无法被检索到的问题。前缀生成使用 prompt caching：同一篇论文的全文只需缓存一次，后续每个 chunk 的调用成本大约降低 90%。

09混合检索与重排

检索链路分为四路召回和两级精排。每个环节都通过消融实验验证收益，没有收益的环节不保留。

图 9-1 · 检索链路

关键技术点

Query 路由

用一个轻量分类器（小模型 + few-shot）把问题分为 factoid、numeric、survey、paper_specific 四类，分别走不同的检索组合和生成模板。survey 类问题自动进入深度研究模式。

RRF 融合

四路召回的分数尺度不同，因此不直接加权求和，而是用 Reciprocal Rank Fusion：score = Σ 1/(60 + rank_i)。这种方法对各路分数的分布不敏感，不需要调参。

Reranker 领域微调

用 QASPER 训练集的（问题、证据段）作为正样本，BM25 检索出的高分非证据段作为难负样本，对 bge-reranker 做 LoRA 微调。预期 NDCG@10 提升 3～5 个点。

父块扩展（Small-to-Big）

用句子级的小块做精确召回，送给 LLM 时扩展到所在段落或相邻段落，兼顾召回精度和上下文完整性。同一章节的多个命中会合并，避免重复。

retrieval/hybrid.pyasync def hybrid_search(q: Query, k: int = 10) -> list[Evidence]:
    dense, sparse, table, graph = await asyncio.gather(          # 四路并发召回
        qdrant.search_dense(q.embedding, filter=q.filters, limit=100),
        qdrant.search_sparse(q.sparse_vec, filter=q.filters, limit=100),
        table_store.query(q) if q.intent == "numeric" else noop(),
        graph_expand(q.seed_papers, hops=1) if q.seed_papers else noop(),
    )
    fused = rrf_fuse([dense, sparse, table, graph], k=60)[:50]
    reranked = await reranker.rerank(q.text, fused, top_k=k)
    return expand_to_parent(reranked, max_tokens=6000)

10深度研究 Agent

深度研究模式用 LangGraph 实现为一个带循环的状态机。设计重点是 Agent 知道什么时候停：通过"证据覆盖度"判断是否继续，不按固定轮数检索。

app = g.compile(checkpointer=PostgresSaver(pool), interrupt_after=["planner"])

覆盖度如何计算

Reflector 为每个子问题列出"回答它需要哪些信息点"，比如"PI 的困惑度""PI 的训练成本"，再逐项判断现有证据是否覆盖。覆盖度等于已覆盖信息点数除以总信息点数。未覆盖的信息点直接转成下一轮的补充查询。这样补检索有明确目标，不会让模型泛泛地"再搜一搜"。

成本控制：Planner、Writer 用强模型；Reflector、Query 改写用小模型。子问题之间并行执行。同一会话内的检索结果用 Redis 缓存，命中条件是 query embedding 的余弦相似度 > 0.95。目标是单次深度研究的成本控制在 $0.15 以内。

11引用校验与反幻觉

这是本项目最核心的差异点。普通 RAG 只会"让模型带上引用"，ScholarLens 会在生成之后验证每条引用是否成立。

01受约束生成Prompt 要求每句话以 [eid] 结尾，eid 只能从给定的证据 ID 中选；输出后用正则校验 eid 是否合法
02句子切分把答案切成"论断 + 引用"对，引用多个来源的句子拆成多条
03NLI 判定用 DeBERTa-v3-large-NLI 计算 P(证据蕴含论断)；数值类论断额外做规则校验，要求数字在原文中出现
04修复蕴含概率低于 0.5 的句子交给 LLM 依据证据重写，只重写一次；仍不通过则删除或标红
05精确定位在证据 chunk 内找出与论断最相似的句子，返回它的 bbox，前端据此精确高亮
verify/citation.pydef verify_claims(answer: str, evidence: dict[str, Evidence]) -> VerifiedAnswer:
    claims = split_claims(answer)                          # [(sentence, [eid, ...]), ...]
    pairs = [(evidence[e].text, c.text) for c in claims for e in c.eids]
    probs = nli.predict_entailment(pairs, batch_size=32)  # GPU 批量推理，约 15ms / 对
    for c, p in zip_claims(claims, probs):
        c.supported = p >= 0.5 and numbers_grounded(c, evidence)
        c.span = locate_span(c.text, evidence[c.best_eid])  # 句级 bbox
    return VerifiedAnswer(claims, trust=mean(c.supported for c in claims))

NLI 阈值 0.5 是初始值，上线前会在 200 条人工标注的"论断-证据"对上，按照 Precision 优先的原则重新标定。

15风险与对策

风险影响对策
MinerU 解析慢且依赖 GPU万篇建库耗时过长评测只用 QASPER 子集；GPU 批处理；同时提供 PyMuPDF 快速模式作为降级方案
表格抽取的 LLM 输出不稳定数值问答出错结构化输出 + 数值必须出现在原表的校验 + 抽样人工核查
Agent 循环成本失控单次研究费用高、耗时长限制最多 3 轮；小模型负责反思；token 预算超限后提前进入 Writer
NLI 模型对长证据判断不准误杀正确句子先在证据中定位最相关的句子，再做 NLI；阈值在人工标注集上标定
论文版权无法公开演示演示只用 arXiv 上开放许可的论文
